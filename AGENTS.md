# Инструкции для помощников проекта

## Начало работы

1. Прочитайте README.md, docs/project-context.md и docs/architecture.md.
2. Проверьте git status и remotes. Не перезаписывайте чужие незакоммиченные изменения.
3. Работайте в папке с package.json. В некоторых окружениях репозиторий вложен в папку site_sql.
4. Источник состояния проекта — файлы и Git, а не предположения из чужого чата.

## Принятые требования

- Интерфейс русский, спокойный и лаконичный. Не добавлять мотивационные лозунги, «Твой маршрут», декоративные подписи и таймеры ученику без запроса.
- В карточке сначала задание, затем обучение; подробное повторение необязательно. Пример не должен автоматически становиться готовым решением при генерации вариантов.
- Сохранять точный текст ошибок SQLite и понятное объяснение.
- Шрифт, отступы, ширины, выравнивание карточек и мобильный экран проверять визуально. Основные актуальные переопределения находятся в app/interface.css после globals.css.
- Навигация: курс / практика / проекты, одна раскрытая тема, до восьми заданий на странице. Общий прогресс в одном месте, вход преподавателя в настройках.
- Учебный SQL выполняется только в изолированной sql.js базе браузера. Никогда не выполнять SQL ученика в D1.
- Ученические варианты устойчивы между входами и устройствами; проектные шаги совместимы. Не менять выданное задание или схему старого снимка молча.
- Перенос гостя не перезаписывает существующие серверные проекты. Переименовывать таблицы под выданный вариант, сохранять строки.

## Работа и проверка

Для изменения вариантов/проектных данных запускайте pnpm check:variants. Для изменений TypeScript — pnpm exec tsc --noEmit; перед отправкой рабочей версии — pnpm build. Проверяйте затронутые сценарии; не добавляйте тесты ради количества.

При изменении D1 обновляйте db/schema.ts и создавайте миграцию с drizzle-kit. Никогда не редактируйте уже применённую миграцию. Проверяйте отдельно локальную и размещённую базы.

Не коммитить .dev.vars, .env*, секреты, данные учеников, .wrangler, dist, node_modules и локальные инструменты. Не выводить пароли или токены в сообщения.

## Документация в каждом содержательном коммите

Обновляйте CHANGELOG.md при изменении поведения. Если изменились запуск, модель данных, варианты, сохранение или ограничения, одновременно обновляйте README.md и docs/architecture.md. В docs/project-context.md фиксируйте новые продуктовые решения и незавершённые важные шаги. Не заявляйте о проверках, которые не выполнялись.

## GitHub и публикация

Перед отправкой сверяйтесь с актуальной общей веткой. Используйте отдельные ветки codex/<задача> и pull request по умолчанию. Не force-push и не удалять работу коллеги.

GitHub и Sites — разные назначения. Последняя инструкция владельца: сначала локально исправить и проверить дизайн. Не публиковать в Sites без нового разрешения на публикацию. Отправка изменений в GitHub не отменяет это ограничение. Развёртывание должно включать нужные миграции D1 до запуска кода, который от них зависит.
