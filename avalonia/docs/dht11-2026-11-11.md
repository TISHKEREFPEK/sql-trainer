# DHT11 · 11 ноября 2026

Продолжение E11, не завершение компонентной матрицы. Добавлена отдельная исполняемая модель `Dht11` / `dht11-single-wire`. Старые Visual-модели сохраняются со своими идентификаторами, контактами и исходным JSON.

## Источники и выбранный профиль

- [Пример Cirkit](https://docs.cirkitdesigner.com/component-simulation-code/76bd66c7-e24d-e1e2-c5b0-259aaba19349), componentId 2568, version 4, flags hasSimulationLogic/isSimulationCodeRunnable true: VDD / DATA / NULL / GND, целочисленные температура 0–50 °C и влажность 20–80 %, начальные 25/60. Это конкретный пример, не вся библиотека Cirkit.
- [Руководство Aosong на сервере Adafruit](https://cdn-shop.adafruit.com/datasheets/DHT11-chinese.pdf): выбран четырёхвыводной профиль 3–5,5 В, целочисленные 0–50 °C / 20–90 % RH, десятичные байты нулевые. Диапазон достоверной влажности зависит от температуры; редактор задаёт идеальные цифровые показания без имитации погрешности, дрейфа и тепловой инерции. Контакт NULL из примера обозначен как NC.
- Руководства разных поколений не смешиваются: [другая редакция Aosong](https://www.haoyuelectronics.com/Attachment/DHT11/DHT11.pdf) задаёт иной минимум питания. Это не универсальная модель любого изделия с надписью DHT11.
- [DHT sensor library 1.4.7](https://github.com/adafruit/DHT-sensor-library/tree/1.4.7), MIT; [Adafruit Unified Sensor 1.1.15](https://github.com/adafruit/Adafruit_Sensor/tree/1.1.15), Apache-2.0. Полные закреплённые библиотеки/лицензии устанавливаются в отдельный SDK, а не копируются в исходники проекта. Сторонние Cirkit source/art не включены; право прямого переноса этих ресурсов не установлено.

## Модель и интеграция

Собственный `dht11.cjs` использует физическое время симуляции. Учитываются прогрев 1 с, LOW старта не менее 18 мс, задержка ответа 20 мкс, преамбула LOW/HIGH по 80 мкс, сорок бит MSB-first с LOW 50 мкс и HIGH 28/70 мкс, завершающий LOW 50 мкс, сумма первых четырёх байтов. Запросы чаще раза в секунду остаются без ответа. Передаётся предыдущее измерение; новое идеальное значение захватывается по окончании ответа. Значения не извлекаются из текста скетча, вызовы Arduino API не подменяются.

AVR подключён через реальные DDR/PORT, input pads и CPU clock events. Pico использует SIO/pad inputs и SimulationClock alarms; чтение SIO согласовано с существующими I2C/SPI input resolvers. Переходы задают настоящий input level, а не только результат read hook. Полная приёмка аппаратных IRQ/PIO/capture комбинаций с датчиком ещё открыта. При warm MCU replacement внешнее устройство сохраняет питание/состояние/оставшиеся переходы.

Native `CircuitDht11` определяет DATA, общую землю и питание по реальным wire/breadboard nets. У bare four-pin датчика нет встроенной подтяжки: внешняя подтяжка определяется по резистору 1–100 кОм к источнику, внутренняя подтяжка MCU учитывается при исполнении. Этот интервал — граница цифрового resolver, не аналоговая модель кабеля/RC. Для Pico рекомендовано питание и подтяжка 3,3 В; прежняя проверка перенапряжения GPIO остаётся. До восьми датчиков с отдельными DATA; превышение можно сохранить, но нельзя запустить. Снятие питания отменяет незавершённую передачу.

Добавлены оригинальный вектор корпуса с четырьмя выводами, SVG, свойства температуры/влажности с изменением во время работы. Эти изменения входят в прежний журнал `control-change`; код, serial output, снимки, сдачи и преподавательская копия используют существующие механизмы. Шаблон DHT.h учитывает физический DATA, прогрев и период 2 с; проверяет `isnan` перед печатью, выводя `DHT11: read error`. Самостоятельный пользовательский код не переписывается.

Новый enum добавлен в конец `PartKind`, серверный inspector принимает `Dht11`. Версия проекта и схема SQLite не меняются; сервер/роли следует обновлять совместно. Скрипты подготовки AVR/Pico и копирования поставки включают обе библиотеки и новый маркер `offline-dht-libraries-v1.json`; существующий неполный/иной SDK не перезаписывается. Старые готовые установщики этих изменений не содержат.

## Проверки и ограничения

Фактические прогоны и найденные ошибки зафиксированы в [едином baseline](next-version-baseline-2026-11-04.md): 30 выбранных regression-проверок и три усиленных native/history сценария прошли. Наборы пересекаются; их не следует суммировать как уникальные тесты. Это доказательства перечисленных сценариев, а не полной аппаратной/аналоговой приёмки.

Первый реальный скетч на Pico прочитал 53/24, но печать NaN после снятия питания дала `inf`: штатный RP2040 float→double путь без `PICO_FLOAT_PROPAGATE_NANS` преобразует такой операнд в бесконечность. [Официальный SDK wrapper](https://github.com/raspberrypi/pico-sdk/blob/master/src/rp2_common/pico_float/float_aeabi_rp2040.S) и находящийся в закреплённом SDK `float_v1_rom_shim_rp2040.S` объясняют это поведение. Модель ROM ради зелёного теста не меняется. Проверка ошибки перенесена на реальный `isnan(float)` до преобразования при печати; она должна доказать, что библиотека вернула NaN, а не произвольное ошибочное число.

Остаются открыты полная аналоговая модель проводки/нагрузки и contention, аппаратная приёмка IRQ/PIO, сочетания со всеми другими деталями, точная графическая приёмка Cirkit, свежий опубликованный комплект и установка/обновление на физических Win10, offline/LAN/нагрузка класса. DHT22/DHT12 и другие датчики этим изменением не объявлены исполняемыми. Импорт отложен владельцем, остальные этапы и матрица продолжаются. Личные установки, базы, Windows policies и GitHub не менялись.
