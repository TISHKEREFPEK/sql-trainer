## E06: внешний kill SQL-писателя · 5 ноября 2026

Два новых сценария `SqlCrashRecoveryTests` прошли (`sql-crash`): тестовый отдельный host фиксирует локальный код/действие/ExecuteRequest, родитель подтверждает активную блокировку второго писателя и завершает host через Process.Kill. После выхода OS освобождает lease; новый store читает тот же код, очередь и UUID. Сценарии до отправки и с уже зафиксированным серверным результатом/потерянным ACK показывают одно итоговое check. В усиленном повторе дополнительно сверяется число checks до явной повторной отправки, чтобы исключить автоматический запуск SQL из Drain.

Режим в test-only Classroom.SandboxProbe, обычный AppContainer-probe сохранён. Job/логи содержат только синтетические учебные данные без API-паролей/токенов; рабочие приложения/личные базы не затронуты. Это процессный kill после завершённого WriteThrough/Flush, не power-loss, дисковый отказ или точный обрыв внутри rename. Эти пункты и весь прочий открытый план остаются. Продуктовый код/схема БД не менялись.

Итоговый целевой прогон `sql-crash-final`: **13 passed**, без пропусков/ошибок — новые два kill-сценария, прежние 10 SQL/восстановительных и прежний реальный crash AppContainer-host. Полная solution заново не тестировалась в этом тестовом шаге; предыдущий общий прогон 27+119 относится к предшествующему изменению приложения.

## E06: явное восстановление повреждённой SQL-копии · 5 ноября 2026

ReadWork проверяет основной файл/backup по одному формату и владельцу. SqlLocalRecoveryException открывает отдельный экран; обычная навигация убирается. Показываются предыдущий код и предупреждение о возможной потере последних изменений, подробности ошибки свёрнуты. RestoreBackup под профильным lease повторно проверяет контекст/хеши, сохраняет повреждённый оригинал `.damaged-GUID`, оставляет backup и атомарно восстанавливает запись. Изменившиеся/чужие/некорректные копии не принимаются. При отсутствии копии новая пустая работа не создаётся.

Восстановленный код Dirty=true, PendingDraft=null: прежняя квитанция сохранения не может отменить повторное CAS-сравнение этого текста с текущим серверным. Сам исходный pending-save остаётся в backup; UUID ExecuteRequest/actions сохраняются, восстановление SQL не запускает. Если серверный черновик новее, получается обычный конфликт с сохранённым восстановленным текстом. После восстановления требуется обычный вход.

Проверки: **10 целевых SQL/восстановительных сценариев passed** (`sql-recovery`), включая native-кнопку 900/1320, точное сохранение повреждённого оригинала, отказ при изменении backup и сохранение кода при серверном расхождении. После проверки чужого профиля/уточнения текста UI полный `sql-recovery-final`: **27 core/API + 119 UI/API passed**, без ошибок/пропусков. После блокировки обычной навигации повторно **3 сценария passed** (`sql-recovery-entry`), включая фактический переход MainWindow.Safe к восстановлению и отсутствие замены файла до нажатия кнопки. Модель БД/протокол сервера/рабочие приложения не менялись. Снимок 900 px просмотрен; это Headless, не приёмка Windows 10/DPI. Настоящие crash/power-loss, массовое повреждение, общая политика архивов/удаления и весь прежний E07–E14 остаются открытыми.

## E06: SQL на диске и подтверждённая доставка · 5 ноября 2026

Добавлены SqlLocalStore и student-only SqlSyncRoutes. Черновик сохраняется до HTTP, pending ExecuteRequest сохраняет исходный код/UUID. Контексты разделены по сертификату/ученику/занятию/WorkScope/заданию. JSON Envelope имеет версию/контрольную сумму, атомарную замену с flush, предыдущую копию и lease единственного писателя. Ошибка записи не меняет последний основной файл/store и не выдаётся за сохранение нового текста. Неизвестный/повреждённый файл не заменяется стартовым шаблоном. Это не полная пошаговая история.

Draft сравнивает базовый хеш серверного текста, сохраняет конфликт без перезаписи и предлагает явный выбор двух вариантов с локальным архивом. Старое занятие принимает только сохранение уже существующей работы своего участника, а receipt читает только исходный результат своего запроса без SQL worker. Старый execute в новом занятии по-прежнему отклоняется. Позднее ограничение не приостанавливает новую пару. Активность не начисляется автоматически за накопленные старые heartbeat.

## E09: компиляция в AppContainer · 5 ноября 2026

Новый FirmwareRunner запускает Arduino CLI и потомков в уникальном AppContainer: отдельный scratch, RX-копия публичных инструментов, чистая среда, явные std handles, без сетевых capabilities и незащищённого fallback. Windows job ограничивает память/число процессов/60 секунд и закрывает дерево при отмене/выходе host. Тестовый host намеренно вызывает Environment.Exit; следующее восстановление убирает его GUID-профиль и точные временные mappings. Записи живых host и непроверенные записи не очищаются по догадке.

## E07/E09: исходное SQL-состояние и проверка попытки · 5 ноября 2026

Преподаватель открывает SQL-попытку из истории, видит закреплённые условие/код/результат и запускает исходный или изменённый SQL отдельно.
